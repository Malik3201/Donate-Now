1. PROJECT OVERVIEW
================================================================================

1.1 What is this project?
-------------------------
Donate Now is a web-based donation management platform for local/community
giving in Pakistan-style contexts (PKR currency, EasyPaisa/JazzCash/bank methods).
It is NOT a payment-gateway checkout app. Donors pay NGOs through offline/digital
wallets or bank transfer, then upload payment proof (screenshot + transaction ID).
NGOs verify proofs; admins oversee users, campaigns, donations, and safety reports.

Primary codebase path: d:\xamp\htdocs\Donate-Now (typical URL: APP_URL in .env,
e.g. http://localhost/Donate-Now)

1.2 What problem does it solve?
-------------------------------
- Lack of transparency in informal donations (no proof trail).
- NGOs managing scattered payment proofs and campaign data.
- Donors unable to track whether a donation was acknowledged.
- Need for admin moderation (fake NGO, fake campaign, fraud reports).
- Volunteers wanting to join campaigns with a clear request/accept flow.

1.3 Target users
----------------
| Role       | Who they are                                      |
|------------|---------------------------------------------------|
| Donor      | Individuals/orgs who give money to campaigns      |
| NGO        | Registered organizations running campaigns        |
| Volunteer  | People offering time/skills for campaigns         |
| Admin      | Platform operators (moderation, analytics)        |
| Guest      | Visitors browsing public home/campaign pages      |

1.4 Main purpose
----------------
Connect donors, verified NGOs, and volunteers on one platform where:
- Every donation has uploaded proof and a visible status (pending/confirmed/rejected/flagged).
- Campaigns go through approval before broad visibility.
- NGOs are verified before full trust signals apply.
- Reports and account controls protect the community.

Reference: index.php (marketing story), includes/CODE_GUIDE.php

3. TECHNOLOGY STACK
================================================================================

3.1 Frontend
------------
- Technology: Server-rendered HTML from PHP templates (NOT React/Vue/Angular).
- JavaScript: Vanilla JS in assets/js/ (landing.js, navbar.js, main.js, forms.js,
  modals.js, dashboard.js, location-map.js, auth-pages.js).
- CSS: Plain CSS files (no Tailwind/Bootstrap as primary framework).
  - assets/css/variables.css, base.css, layout.css, components.css
  - assets/css/landing.css (home)
  - assets/css/dashboard.css (logged-in app)
  - assets/css/dashboard-responsive.css
  - assets/css/auth.css
  - assets/css/static-pages.css
  - assets/css/mobile-app.css (max-width media queries only)
  - assets/css/brand.css, forms.css, tables.css, location-map.css
- Fonts: Google Fonts (Inter) via includes/public_header.php
- Maps: Leaflet + OpenStreetMap + Nominatim (assets/js/location-map.js)
- State management: None (no Redux/Vuex). State = PHP session + page reload.
- Build tools: Not clearly found in codebase (no package.json, no Vite/Webpack).

3.2 Backend
-----------
- PHP 8+ (declare(strict_types=1) used widely).
- Architecture: Page-based PHP (each .php file = one route/screen or POST handler).
- No Laravel/Symfony/CodeIgniter framework detected.
- No separate REST API layer; json_response() exists in includes/functions.php but
  is NOT clearly used by other files for AJAX APIs.

3.3 Database
--------------
- MySQL (InnoDB), schema in database/schema.sql
- Access: PDO via config/database.php → db()
- Migrations: database/migrations/add_location_columns.sql +
  database/run_migration.php (manual runner)

3.4 Authentication
------------------
- PHP sessions ($_SESSION['user_id'], role, email, full_name).
- Passwords: password_hash() / password_verify() (bcrypt default).
- Guards: includes/auth_check.php (login + active account),
  includes/role_check.php (role whitelist per page).
- CSRF: csrf_token() / verify_csrf_token() on sensitive POST forms.
- Password reset: password_resets table + auth/forgot_password.php,
  auth/reset_password.php.

3.5 APIs
--------
- Not a JSON REST API application.
- "Endpoints" are PHP file paths; browser uses GET (pages) and POST (forms).
- External HTTP calls: Brevo (email), ImageKit (uploads) from server-side PHP.

3.6 Package manager / deployment
--------------------------------
- No Composer.json clearly found in project root scan.
- No npm/package.json.
- Deployment target: Typical PHP hosting (Apache/XAMPP, shared VPS, cPanel).
  Not designed for Vercel/Netlify (static) as primary — needs PHP + MySQL.

5. BACKEND ANALYSIS
================================================================================

5.1 Architecture pattern
------------------------
Classic "PHP page + include" architecture:
  Browser → Apache → specific .php file
    → config/database.php + includes
    → auth_check / role_check (if protected)
    → business logic + SQL in same file (or small helpers)
    → HTML output or redirect()

There are no separate Controller/Model classes in MVC sense. Database tables are
queried directly with PDO prepared statements in page files.

5.2 Request–response flow (typical protected page)
--------------------------------------------------
1. User requests /donor/browse_campaigns.php (GET).
2. auth_check.php: session? active account? → $authUser, $pdo.
3. role_check.php: require_role(['donor']).
4. dashboard_layout_start.php: HTML head, sidebar, topbar, open content.
5. Page runs SELECT queries, renders HTML.
6. dashboard_layout_end.php: footer, scripts.

POST action example (ngo/donation_action.php):
1. POST only; else 405.
2. Verify CSRF + role.
3. UPDATE donations, campaigns, profiles; INSERT history; notifications; emails.
4. redirect() back to listing/detail.

5.3 Security
------------
| Concern           | Implementation                                      |
|-------------------|-----------------------------------------------------|
| Authentication  | Session user_id                                     |
| Authorization   | role_check.php per directory                        |
| Account state   | account_status must be 'active' to use app          |
| CSRF            | csrf_token on forms                                 |
| XSS             | sanitize() = htmlspecialchars on output             |
| SQL injection   | PDO prepared statements (observed pattern)          |
| Passwords       | password_hash / password_verify                     |
| File uploads    | ImageKit or validated upload helper                 |
| Admin actions   | require_role(['admin']) on admin/* actions          |

5.4 Error handling
------------------
- Many action scripts: exit('plain text message') on validation failure.
- DB connection failure: config/database.php exits with HTTP 500 message.
- Registration: try/catch with transaction rollback.
- Not a unified JSON error middleware.

5.5 Email & notifications
---------------------------
- includes/mail_helper.php — Brevo API or SMTP (config/brevo.php).
- includes/notification_helper.php — INSERT into notifications table.
- Triggers: registration, donation proof, NGO verify, campaign status, etc.

5.6 File uploads
----------------
- includes/upload_helper.php → ImageKit API (config/imagekit.php).
- Used for: campaign images, donation proof, profile photo, report attachments.
- ui_helpers.php image_or_placeholder() when no image URL.

9.1 Convention
----------------
- GET  = display page (unless action-only script)

- Auth = Session cookie required
- CSRF = csrf_token field required on POST (where implemented)

10. DATABASE / DATA MODELS
================================================================================

Database name (schema): donate_now

10.1 Core tables
----------------

users
  Purpose: Login account for all roles.
  Key fields: email (unique), password (hash), role (admin|donor|ngo|volunteer),
  account_status (active|inactive|blocked|suspended|temporary_hold),
  profile_photo_url, email_verified.

donor_profiles
  Purpose: Donor-specific data (1:1 users).
  FK: user_id → users.id
  Fields: address, donor_type, total_donations_count, total_donated_amount.

ngo_profiles
  Purpose: NGO organization profile (1:1 users).
  FK: user_id → users.id
  Fields: ngo_name, registration_number, description, address,
  latitude, longitude, verification_status, totals.

volunteer_profiles
  Purpose: Volunteer skills/availability (1:1 users).
  FK: user_id → users.id

10.2 Campaigns & donations

campaign_categories
  Purpose: Optional category labels for campaigns.

campaigns
  Purpose: Fundraising campaigns owned by NGO.
  FK: ngo_id → ngo_profiles.id, category_id → campaign_categories.id
  Key fields: title, description, target_amount, collected_amount,
  status (pending|approved|rejected|active|completed|temporary_hold),
  image_url, location_label, lat/long, dates.

campaign_updates
  Purpose: Progress news posts on a campaign.
  FK: campaign_id → campaigns.id

ngo_payment_methods
  Purpose: How donors pay this NGO (wallet/bank details).
  FK: ngo_id → ngo_profiles.id
  Fields: method_type (easypaisa|jazzcash|bank|other), account numbers.

donations
  Purpose: One donation attempt with proof.
  FK: donor_id → donor_profiles.id, ngo_id, campaign_id, payment_method_id
  Key fields: amount, transaction_reference, proof_image_url,
  status (pending|confirmed|rejected|flagged), verification note, timestamps.

donation_status_history
  Purpose: Audit trail of status changes.
  FK: donation_id, changed_by_user_id

10.3 Volunteers

volunteer_campaigns
  Purpose: Join request / membership.
  FK: volunteer_id, campaign_id, ngo_id
  status: pending|accepted|rejected|cancelled

10.4 Trust & safety

reports
  Purpose: User-submitted complaints.
  FK: reporter_user_id, optional reported_user/campaign/donation
  report_type: fake_payment, fake_ngo, fake_campaign, abuse, fraud, etc.
  status: open|under_review|resolved|rejected

account_status_history
  Purpose: Admin changes to user account_status.

admin_notes
  Purpose: Internal admin notes on users/campaigns/donations/reports.

notifications — per-user in-app messages.

11.1 Requirements
-----------------
- PHP 8.0+ with extensions: pdo_mysql, mbstring, curl, fileinfo (recommended)

11.2 Local setup (XAMPP example)
--------------------------------
1. Clone/copy project to htdocs/Donate-Now
2. Create MySQL database:
     mysql -u root -p < database/schema.sql
   Or import database/schema.sql via phpMyAdmin.
3. Optional location columns if schema older:
     php database/run_migration.php
4. Create .env in project root (copy from team template):
     APP_URL=http://localhost/Donate-Now
     DB_HOST=localhost
     DB_NAME=donate_now
     DB_USER=root
     DB_PASS=
     (plus Brevo and ImageKit keys if testing email/uploads)
5. Start Apache + MySQL in XAMPP.
6. Open APP_URL in browser.

11.3 Create admin user (development)
------------------------------------
     php database/seed.php
   Default from seed (see database/seed.php): admin@localdonation.com / admin123
   Change immediately in production.

11.4 Frontend / backend run separately?
----------------------------------------
Not applicable — single PHP application. No separate Node dev server.

11.5 Troubleshooting setup
--------------------------
- Blank page: enable PHP error log; check DB credentials in .env.

- Upload fails: configure ImageKit keys or check upload_helper fallback behavior.

13.1 What is Donate Now? (for end users)
----------------------------------------
Donate Now helps you support local causes with clear records. You choose a
campaign, pay the NGO using their Easypaisa/JazzCash or bank details, then upload
your payment screenshot and transaction ID. The NGO reviews your proof and marks
the donation as confirmed when valid.

13.2 Getting started as a Donor
-------------------------------
1. Click "Create Account" or Register on the website.
2. Choose "Donor" as your role.
3. Log in and open "Browse Campaigns."
4. Pick a campaign you want to support (only approved/active campaigns accept donations).
5. Click Donate and follow the steps:
   - Note the NGO payment account details.
   - Send money using your phone wallet or bank app.
   - Enter the amount and transaction ID (TID) exactly as on your receipt.
   - Upload a clear screenshot of the payment.
6. Wait for the NGO to confirm. Check "My Donations" for status.

13.3 Getting started as an NGO
------------------------------
1. Register as NGO (provide organization details).
2. Wait for platform admin to verify your NGO.
3. Add at least one Payment Method (Easypaisa/JazzCash/Bank).
4. Create a campaign (title, goal, story, image).
5. Wait for admin to approve the campaign.
6. When donors submit proofs, open Donation Dashboard and Confirm or Reject each one.
7. Manage volunteer requests from the Volunteer Requests page.

13.4 Getting started as a Volunteer
-----------------------------------
1. Register as Volunteer.
2. Browse campaigns and send a Join request with a short message.
3. If the NGO accepts, you will see the campaign under My Campaigns.

15.2 Security recommendations
-------------------------------
- Force HTTPS in production; set secure session cookie flags (not clearly in codebase).
- Remove default admin seed credentials on production servers.
- Restrict admin/email_test.php to trusted IPs or remove after testing.
- Ensure .env is not web-accessible.
- Rate-limit login and forgot-password (not clearly found).
- Regular backups of MySQL.

15.3 Performance recommendations
-------------------------------
- Add DB indexes on frequently filtered columns (status, ngo_id, campaign_id) if slow.
- Cache heavy analytics queries on admin/analytics.php if data grows.
- Optimize landing page external images (many hotlink URLs in index.php).

- Introduce a thin routing layer or framework for maintainability if team grows.
